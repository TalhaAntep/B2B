# Deep legacy persistence reverse engineering

## Current consolidated release status — 2026-11-22

This status supersedes earlier discovery and milestone snapshots in this report. Those dated findings remain as historical evidence and are not current-state claims.

- The UI catalog contains 98 unique DealerSystemSetting control IDs. The authenticated Development-only settings API has a fixed allowlist of 93 setting adapters; five image controls use the separate application-owned asset service.
- Five setting controls use application-owned extension keys because no legacy destination was established: `ParameterProductDetailNotLogin2`, `ParameterMenu2`, `WhatsAppOrderNotification`, `FavoriteIconPosition`, and `FavoriteIconVerticalPosition`. Their new-app save/readback/restoration was tested; old-portal reads remain unverified. `ParameterProductSearch` is hybrid: its low 16-bit word is stored in candidate `DealerSettings.ParameterProductSearch` (`smallint`), and its high word in an application-owned extension key.
- `ParameterPayment` is persisted as the same unsigned 16-bit bit pattern in SQL `smallint` using signed representation. `ParameterModules` option `1` belongs to `ddlParameterModules` / `DealerSettings.ParameterModules` (`int`); `ParameterAdmin` option `32` belongs to the separate `ddlParameterAdmin` / `DealerSettings.ParameterAdmin` (`bigint`).
- Legacy save-handler parity remains unverified for all 98 controls because the original server-side Web Forms handler is unavailable.
- Current normal API mode is read-only; isolated test-write flags are disabled. Final SQL checks were SELECT-only against `Store5_Settings_Test` and the unique `MemberCode=store5` row. No database writes or public deployment occurred during this final delivery pass.
- Historical test and backup evidence is retained in the SQL/test reports. Backend test suites and SQL integration groups were not rerun during this delivery pass; only frontend tests/build and backend Release build are current-run results.

**Scope:** the 81 controls that were draft-only before this review (the earlier 17 adapter-tested controls are excluded from the detailed table). Evidence was collected from the local v2 control inventory, generated catalog/mapping, `Store5_Settings_Test`, and SQL module definitions. Only the unique `MemberCode=store5` settings row was selected. No raw setting values, file paths, script contents, credentials, or connection strings are recorded.

## Executive findings

- Audited controls: **81 / 81**. Source control IDs/options were checked against the generated inventory and catalog.
- SQL objects inspected: **130** user SQL module definitions (69 procedures, 37 scalar functions, 2 table-valued functions, 3 triggers, 19 views); all definitions were available. No stored module contained a direct `UPDATE dbo.DealerSettings` or `INSERT dbo.DealerSettings` save statement. The original ASP.NET Web Forms C# save handler remains unavailable; the newly supplied `FormManagement.js` is present, but the exported settings page does not call `FormToParameters`.
- Direct consumer semantics were found for four candidates: `Schedule`, `HasStockVisible`, `ParameterIntegration`, and `MinStockFilter`. These do **not** establish the missing Web Forms save serialization.
- New isolated adapter fields: **21** (16 numeric single-selects and 5 SQL `bit` checkboxes). Each passed a backup-verified persistent update, SQL read-back, and exact original-value restoration in `Store5_Settings_Test`; legacy Web Forms parity remains unknown.
- Total adapter-persisted fields now tested in local test mode: **38 / 98**. Normal API mode remains read-only and reports zero editable settings.
- Legacy save behavior verified: **0 / 98**. A new API adapter round trip is not evidence of the old `lbSaveAndExit` handler behavior.
- `UseFiltering` remains unresolved: its candidate column is nullable `nvarchar(250)`. The generic helper can comma-join multi-select values, but page-to-helper linkage and backend storage encoding remain unknown; the browser snapshot is not verified as the store5 row.
- The generic client helper implements comma joining for multi-selects, but no evidence links that helper to the settings postback or establishes C# persistence of CSV. Numeric-looking SQL text or a multi-select UI does not prove stored encoding.

## SQL module definition review

The module source review distinguishes a settings consumer from a same-named column used by another entity. The SQL catalog returned no column-level `sys.sql_expression_dependencies` rows for `DealerSettings`; source review therefore checked each definition and the surrounding SQL context. No user module contains a direct `UPDATE`/`INSERT` of `DealerSettings` settings. This says nothing about missing Web Forms code or non-SQL application code.

No module established a delimited, JSON, or XML encoding for the listed settings; the generic JS CSV helper is not a SQL storage proof. The direct findings above are the only field-specific storage-consumer evidence accepted.

## Serialization classification

### Bitmask and multi-select

- `UseFiltering`: four source values `2, 4, 8, 16` are powers of two, but the candidate is `nvarchar(250)` and the current row contains numeric-looking text. No module consumes the column. Delimiter/bitmask/scalar encoding is unresolved; do not write.
- `Schedule`: only source value `1`; SQL consumer treats it as a scalar 1/0-style flag. It is a one-option multiple-select control, not an established general bitmask. Stock import behavior makes it unsafe to test here.
- `ParameterProductSearch`, `ParameterPayment`, `ParameterLogin`, `ParameterLoginMenu`, `ParameterAdmin`: their source option keys are powers of two and candidate SQL columns are integral, but no direct DealerSettings consumer confirms the encoding. Do not infer bitmasks solely from these facts.
- `ParameterIntegration`: SQL consumer definitions confirm bitwise predicates for flags 1, 2, and 4; remaining bits and full legacy save behavior are unverified. No write test due external customer/order import effects.
- `ParameterModules`: original browser DOM evidence identifies option `1` (“Show Order Export Button”). The separate `ParameterAdmin` control independently uses option `32` for the same label. The option mapping is resolved; original legacy save-handler behavior remains unavailable.
- `ParameterProductDetailNotLogin2`, `ParameterMenu2`: no candidate column; their source option keys cannot establish storage.
- No delimited-string, JSON, or XML multi-select serialization was found.

### Scalar and Boolean

- The 16 newly tested select fields have one selected source string each, SQL `int`, and the pre-test `store5` values matched one of the original option strings. The adapter validated the allowlisted source key/value, used typed parameters, concurrency predicates, read-back, and restoration.
- The five newly tested checkbox fields map to actual SQL `bit`; they loaded as non-NULL Boolean values. The adapter accepted only JSON Boolean values and the test restored each exact original bit.
- Other bit-backed dropdowns (`UseCurrencyType`, `ExpiryDate`, `Integrated`, `BonusShow`) were not added because the adapter/UI contract needs explicit 0/1-to-bit serialization or the setting concerns currency/integration. `CommonSystem` is NULL; `DiscountType` does not match its source options.
- Other integer and text inputs such as colors, URLs, dealer text, E-Invoice, and payment link remain drafts until range, culture, validation, empty/NULL, and operational behavior are established. `MinCartCount`, `MinCartTotal`, `MaximumOrderQuantity`, and `MinStockFilter` subsequently passed isolated application-adapter tests; this does not verify legacy validation or invoke the SQL stock export behavior.

### File/path fields

The five inventoried uploads map only to candidate text columns: `Logo`, `Logo2`, `LogoLogin`, `Favicon`, and `NoImageImage`. Existing text/null states were inspected with content withheld. No SQL module establishes whether the bytes live in SQL, local filesystem, or remote storage; path/URL naming, MIME/size checks, replace/delete cleanup, and cache behavior are unknown. No upload or deletion was executed. Do not persist a client filename as a substitute for upload handling.
